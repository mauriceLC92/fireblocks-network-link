## Repository Overview

This repository contains the OpenAPI specification for the Fireblocks Network Link (also known as Fireblocks Provider Connectivity API), which enables third-party providers (exchanges, banks, on/off-ramp services) to integrate with the Fireblocks platform.

### Two Versions

- **v1**: Legacy version with OpenAPI spec at root level (`openapi.yaml`)
- **v2**: Current version at `v2/` with modular OpenAPI specs and a validation tool

The v2 implementation is the focus of active development.

## Architecture

### v2 Structure

```
v2/
├── openapi/           # OpenAPI specification files
│   ├── fb-provider-api.yaml              # Base API (capabilities, accounts, balances)
│   ├── fb-provider-transfer-api.yaml     # Transfer operations
│   ├── fb-provider-trading-api.yaml      # Trading operations
│   ├── fb-provider-collateral-api.yaml   # Off-Exchange/Collateral integration
│   ├── fb-provider-liquidity-api.yaml    # Liquidity operations
│   ├── fb-provider-ramp-api.yaml         # On/off-ramp operations
│   ├── fb-provider-subscription-api.yaml # Subscription operations
│   └── fb-unified-openapi.yaml           # Generated unified spec (DO NOT EDIT)
└── api-validator/     # Validation tool with mock server and tests
    ├── src/
    │   ├── client/    # Generated OpenAPI client
    │   ├── config/    # Configuration management (uses convict + env vars)
    │   ├── security/  # Request signing (HMAC, RSA, ECDSA)
    │   ├── server/    # Mock server implementation (Fastify)
    │   └── utils/     # Shared utilities
    └── tests/
        ├── sanity-tests/  # Critical server functionality tests
        ├── self-tests/    # Validation tool unit tests
        └── server-tests/  # API validation tests
```

### Key Concepts

**Modular API Design**: The API is split into optional components (transfers, trading, liquidity, ramps, etc.) that providers can selectively implement. The `/capabilities` endpoint is used for dynamic discovery of supported features.

**Two-Way Integration**: The Collateral (Off-Exchange) capability enables bidirectional communication between Fireblocks and providers, allowing traders to maintain control of assets while using exchange services.

**Transfer Methods**: The API supports multiple transfer methods (public blockchain, IBAN, SWIFT, ACH, SEPA, internal transfers, p2p) with a unified pattern across deposit and withdrawal operations.

**Security**: All requests include cryptographic signatures using HMAC, RSA, or ECDSA. The validation tool supports all three methods with configurable encoding options.

### OpenAPI Specification Workflow

**When modifying the API**:

1. Edit the relevant `fb-provider-*-api.yaml` files in `v2/openapi/`
2. Generate the unified spec:
   ```bash
   cd v2/api-validator
   npm run make-unified-openapi
   ```
3. Lint the OpenAPI spec (requires Docker):
   ```bash
   cd v2/openapi
   ./lint-openapi.sh
   ```
4. Generate the TypeScript client:
   ```bash
   cd v2/api-validator
   npm run generate-openapi-client
   ```
5. Restart the mock server and run tests

**NEVER edit `fb-unified-openapi.yaml` directly** - it is auto-generated from the modular spec files.

**NEVER edit `src/client/generated/` directly** - it is auto-generated by `npm run generate-openapi-client`.

### Utility Scripts

Scripts for manually hitting a live server — useful for exploratory testing and debugging. They read config from `.env` (or `.env.<target>` when `TARGET` is set) and save responses as pretty-printed JSON to `scripts/output/` (gitignored).

```bash
npm run scripts:ui                               # Browser UI: pick script + env + payload
npm run scripts:accounts                         # List all accounts
npm run scripts:ramps-caps -- <accountId>        # Get ramp capabilities for an account
npm run scripts:list-ramps -- <accountId>        # List ramps for an account
npm run scripts:get-ramp -- <accountId> <rampId> # Get a specific ramp
npm run scripts:create-quote                     # Generate a quote
npm run scripts:momo-onramp                      # Create a MoMo on-ramp
npm run scripts:momo-offramp                     # Create a MoMo off-ramp
npm run scripts:lbt-onramp                       # Create an LBT on-ramp
npm run scripts:lbt-offramp                      # Create an LBT off-ramp
npm run scripts:bridge-ramp                      # Create a bridge ramp (crypto -> crypto)
npm run scripts:get-rate -- <accountId> <rampsPairId>  # Get rate for a ramps pair
npm run download-server-capabilities             # Download capabilities from configured server
```

`<accountId>` can be omitted when `ACCOUNT_ID` is set in the active env file; an explicit argument still wins.

Request bodies live in `scripts/payloads/` as JSON, one file per scenario (`<script>.<variant>.json`). Each script has a default; select another with `--payload <name>`, and pass a bad name to list them all. A `$comment` key is stripped before sending. Ramp-creation scripts generate a fresh `idempotencyKey` per run, so every run creates a new ramp — to test idempotency, hard-code `idempotencyKey` in the payload file and run it twice.

`npm run scripts:ui` serves a local-only page (127.0.0.1:8100) for choosing a script, environment, and payload, editing the request body, and watching output stream live. It shells out to the same commands as the CLI. Production targets require a confirming second click.

Liquidity scripts (`scripts/liquidity/`) don't yet have npm aliases — run them directly with `ts-node scripts/liquidity/<script>.ts`.

## Configuration

### Environment Variables

The validation tool uses environment variables for configuration. Copy `v2/api-validator/.env.example` to `.env` and configure:

- `SERVER` - Base URL of the server to test (default: http://0.0.0.0:8000/v2)
- `PORT` - Mock server port (default: 8000)
- `NODE_ENV` - Environment (development/test/production)
- `LOG_LEVEL` - Logging verbosity (fatal/error/warn/info/debug/trace/silent)
- Authentication settings (API keys, signing method, encoding)
- Withdrawal destinations and test data

See `v2/api-validator/src/config/index.ts` for all available configuration options.

### Mock Server Presets

The mock server supports capability presets located in `v2/api-validator/capability-presets/`:
- `all-capabilities/` - Full API support
- `internal-transfers-only/` - Limited to internal transfers

## Testing Patterns

### Test Structure

- **Sanity tests** - Must pass before other tests run. Test critical server functionality.
- **Self tests** - Unit tests for the validation tool's internal code.
- **Server tests** - Full API validation against the mock server or external server.

### Running Tests Against Your Server

1. Configure `.env` with your server URL and credentials
2. Set withdrawal destinations and other test parameters
3. Run `npm test`

Test reports are generated in JSON and HTML formats in the validator root directory.

## Key Implementation Details

### Request Signing

All API requests must be signed. The signature is computed by:

1. Building the message: `{timestamp}{nonce}{METHOD}{endpoint}{body}`
2. Applying pre-encoding (URL-encoded, base64, hexstr, base58, or base32)
3. Signing with HMAC, RSA, or ECDSA
4. Applying post-encoding (base64, hexstr, base58, or base32)

The validation tool in `src/security/` implements all signing methods.

### Idempotency

The API requires idempotency keys for operations that create or modify resources. The server must:
- Return the same response for retries with the same idempotency key
- Detect and reject reuse of idempotency keys with different requests
- Remember idempotency keys for at least 7 days

### Pagination

List endpoints use cursor-based pagination with `limit`, `startingAfter`, and `endingBefore` query parameters. The validation tool includes comprehensive pagination tests.

### Mock Server Architecture

**Route auto-registration**: `src/server/routes.ts` iterates over all OpenAPI endpoint schemas and looks for a handler function in `src/server/handlers/` whose name exactly matches the endpoint's `operationId`. If found, that handler is used; otherwise a dummy handler is registered with a warning. Adding a new endpoint handler requires the function name to match the operationId.

**Per-account controllers**: `ControllersContainer<T>` (in `src/server/controllers/controllers-container.ts`) lazily instantiates a controller per account ID. `Repository<T>` provides generic in-memory CRUD storage. All mock server state is in-memory and resets on server restart.

**Capability presets**: If `MOCK_SERVER_CAPABILITIES_DIR` is set, the mock server loads JSON files from that directory (e.g. `capability-presets/all-capabilities/`) to pre-populate accounts, assets, and capabilities. Without a preset, data is randomly generated by `json-schema-faker`.

### Test Capability-Skipping Pattern

Server tests skip entire test suites for API components the server doesn't support. `tests/utils/capable-accounts.ts` provides `hasCapability()` / `getCapableAccountId()` helpers that read capabilities fetched by the Jest global setup (`tests/setup/preload-capabilities.ts`). Tests use `describe.skipIf(condition)` and `it.skipIf(condition)` (extended in `tests/setup/conditional-tests.ts`) to conditionally skip.

## Development Guidelines

- The OpenAPI specs use OpenAPI 3.0.0 format
- TypeScript is configured with strict mode enabled
- The mock server uses Fastify with fastify-openapi-glue for request/response validation
- All API data uses JSON format
- Asset IDs and amounts are represented as strings to preserve precision
- The codebase uses pino for structured logging
